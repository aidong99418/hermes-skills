# 🔍 代码审查框架

## 五维度审查清单

### 1. Correctness（正确性）⚠️
- [ ] 功能逻辑与需求一致
- [ ] 边界条件处理（空值/极端值/并发）
- [ ] 错误处理是否有fallback
- [ ] 单元测试覆盖率足够
- [ ] 第三方库版本兼容性

### 2. Readability（可读性）📖
- [ ] 变量/函数命名语义清晰
- [ ] 函数长度适中（建议<50行）
- [ ] 注释说明WHY而非WHAT
- [ ] 代码结构层次分明
- [ ] 没有magic number/硬编码

### 3. Architecture（架构）🏗️
- [ ] 模块边界清晰，耦合度低
- [ ] 依赖注入而非硬依赖
- [ ] 配置与代码分离
- [ ] 遵循SOLID原则
- [ ] 可扩展性预留接口

### 4. Security（安全）🔒
- [ ] 输入验证和清理
- [ ] 无SQL注入/命令注入风险
- [ ] 敏感信息不硬编码（密钥/密码）
- [ ] 权限控制合理
- [ ] 日志不泄露敏感数据

### 5. Performance（性能）⚡
- [ ] 无N+1查询问题
- [ ] 合理使用缓存
- [ ] 大循环无阻塞主线程
- [ ] 图片/资源懒加载
- [ ] 数据库索引合理

## 输出格式

```markdown
## 代码审查报告

### ✅ 亮点（至少一条正面反馈）
- ...

### 🔴 Critical（必须修复）
- ...

### 🟡 Important（建议修复）
- ...

### 💡 Suggestion（可选优化）
- ...

### 📊 总体评分
- 正确性: X/10
- 可读性: X/10
- 架构: X/10
- 安全: X/10
- 性能: X/10
```

## 审查技巧
1. **先读测试** — 理解预期行为
2. **再跑一遍** — 验证理解是否正确
3. **按维度扫** — 每维度找到1-2个最重要问题
4. **给一条正面** — 每条Critical前先给一条亮点

## 使用场景
- 收到代码链接或文件路径时自动触发
- pull request review
- 上线前质量门禁
- 代码重构前的现状评估
