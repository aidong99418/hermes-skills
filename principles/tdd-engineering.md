# TDD工程实践（mattpocock）

## 核心原则

**测试通过公共API验证行为，不测试实现细节。**
代码可以完全重构，测试不应该坏。

好测试 = 集成风格：真实调用公共API，像规格说明书一样描述"系统能做什么"。
坏测试 = 耦合实现：mock内部协作方、测试私有方法、通过数据库查询而非接口验证。

## 致命反模式：水平切片

**❌ 不要：先把所有测试写完，再一次性实现所有代码**

这会生产"形状测试"——测试的是数据结构/函数签名，而非用户面对的行为。
测试变得不敏感：行为坏了还能过，实现重构了就挂。

**✅ 正确：垂直切片（Tracer Bullet）**

一个测试 → 一个实现 → 重复。每一轮从实际代码中学到新东西。

```
错误（水平）：
  红色：test1, test2, test3, test4, test5
  绿色：impl1, impl2, impl3, impl4, impl5

正确（垂直）：
  红→绿：test1 → impl1
  红→绿：test2 → impl2
  红→绿：test3 → impl3
```

## 工作流

### 1. 规划（Plan）
- [ ] 与用户确认需要哪些接口变更
- [ ] 确认测试哪些行为（按优先级）
- [ ] 识别深模块机会（简单接口、深实现）
- [ ] 设计接口的可测试性
- [ ] 列出要测试的行为（不是实现步骤）
- [ ] 获得用户批准

### 2. Tracer Bullet（第一发）
```
红色：写第一个测试 → 测试失败
绿色：写最少量代码通过测试 → 通过
```
这是你的Tracer Bullet——证明路径端到端可行。

### 3. 增量循环
每个行为重复：
```
红色：写下一个测试 → 失败
绿色：写最少量代码通过 → 通过
```
规则：
- 一次只写一个测试
- 只写刚好通过当前测试的代码
- 不为未来测试做预期
- 聚焦于可观察行为

### 4. 重构（所有测试通过后）
- [ ] 消除重复
- [ ] 加深模块（把复杂度藏在简单接口后）
- [ ] 顺手应用SOLID原则
- [ ] 考虑新代码揭示了关于现有代码的什么
- **每步重构后运行测试**

**永远不在RED时重构。先到GREEN再说。**

## 每轮检查清单

```
[ ] 测试描述行为，不是实现
[ ] 测试只用公共接口
[ ] 测试能承受内部重构
[ ] 代码对这个测试是最小化的
[ ] 没有加入投机性功能
```
