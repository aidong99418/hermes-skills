# Test-Driven Development

## 核心原则

**测试通过公共接口验证行为，不验证实现细节。** 代码可以完全重构，测试不应该坏。

**好的测试** 是集成风格：通过公共API走真实代码路径。像规格说明书一样读："用户可以用有效购物车结账"告诉你存在什么能力。这种测试能经受重构考验。

**坏的测试** 耦合到实现：mock内部协作者、测试私有方法、通过外部手段验证（直接查数据库而非用接口）。标志信号：重构后行为没变但测试坏了——那测试测的是实现，不是行为。

## 反模式：水平切片 ❌

**不要先写所有测试，再写所有实现。** 这叫"水平切片"——把RED当成"写全部测试"，GREEN当成"写全部代码"。

这会产生**垃圾测试**：
- 批量写的测试测的是"想象的行为"，不是"实际的行为"
- 测的是数据的形状（数据结构、函数签名），不是用户可见的行为
- 测试变得不敏感——行为坏了它通过，行为好好的它报错

**正确方法：垂直切片 tracer bullet。** 一个测试 → 一个实现 → 重复。每个测试回应你从上一轮学到的东西。因为刚写完代码，你精确知道什么行为重要以及如何验证。

```
❌ 错误（水平）:
  RED:   test1, test2, test3, test4, test5
  GREEN: impl1, impl2, impl3, impl4, impl5

✅ 正确（垂直）:
  RED→GREEN: test1→impl1
  RED→GREEN: test2→impl2
  RED→GREEN: test3→impl3
  ...
```

## 工作流

### 1. 规划

写代码前：
- [ ] 确认需要什么接口变更
- [ ] 确认测什么行为（按优先级排列）
- [ ] 识别深模块机会（小接口、深实现）
- [ ] 为可测试性设计接口
- [ ] 列出要测的行为（不是实现步骤）
- [ ] 获取用户对计划的认可

问："公共接口应该长什么样？哪些行为最重要？"

**你不可能测所有东西。** 确认用户最关心哪些行为。把测试精力集中在关键路径和复杂逻辑上。

### 2. Tracer Bullet

写**一个**测试，确认系统的一件事：

```
RED:   写第一个行为的测试 → 测试失败
GREEN: 写最小代码让它通过 → 测试通过
```

这是你的 tracer bullet——证明这条路端到端走得通。

### 3. 增量循环

对每个剩余行为：

```
RED:   写下一个测试 → 失败
GREEN: 最小代码让它通过 → 通过
```

规则：
- 一次只写一个测试
- 只写够通过当前测试的代码
- 不预判未来测试
- 保持测试聚焦在可观察行为

### 4. 重构

所有测试通过后，寻找重构候选：
- [ ] 提取重复
- [ ] 加深模块（把复杂性移到简单接口后面）
- [ ] 自然地应用SOLID原则
- [ ] 考虑新代码揭示了现有代码的什么
- [ ] 每步重构后跑测试

**RED时绝不重构。先到GREEN。**

## 每轮检查清单

```
[ ] 测试描述的是行为，不是实现
[ ] 测试只通过公共接口
[ ] 测试能经受内部重构存活
[ ] 代码对这个测试来说是最小化的
[ ] 没有添加投机性功能
```
