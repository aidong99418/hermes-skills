# Grill with Docs

用苏格拉底式追问来穷尽计划的每个方面，直到达成共识。沿着设计树的每个分支走，一个一个解决决策间的依赖关系。每个问题给出推荐答案，等待反馈再继续。

如果问题可以通过探索代码库回答，就去探索代码库。

## 域-awareness

探索代码库时，同时找现有文档：

### 文件结构

大多数仓库有一个单一上下文：
```
/
├── CONTEXT.md          ← 术语表
├── docs/
│   └── adr/            ← 架构决策记录
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果有 `CONTEXT-MAP.md`，说明有多个上下文。地图指向各自位置。

文件懒创建——只有确实要写时才创建。如果不存在 `CONTEXT.md`，第一个术语解决时创建一个。如果不存在 `docs/adr/`，第一个ADR需要时创建。

## 追问技巧

### 挑战术语表

当用户用的术语与 `CONTEXT.md` 中现有语言冲突时，立即指出。"你的术语表定义'取消'为X，但你好像在指Y——到底是哪个？"

### 磨光模糊语言

当用户用模糊或重载的术语时，提出精确的规范术语。"你说'账户'——你指的是客户还是用户？这两者不同。"

### 讨论具体场景

当讨论域关系时，用具体场景压力测试。发明探测边缘情况的场景，迫使用户精确界定概念边界。

### 交叉验证代码

当用户说某东西如何工作，检查代码是否同意。如果发现矛盾，将其暴露："你的代码取消了整个订单，但你刚说支持部分取消——哪个是对的？"

### 内联更新CONTEXT.md

当术语解决时，立即更新 `CONTEXT.md`。不要批量处理——随着发生就捕获。`CONTEXT.md` 应该完全不含实现细节。它是术语表，不是规格说明、不是草稿本、不是实现决策的存储库。

### 审慎给出ADR

只在三个条件都满足时才给出ADR建议：

1. **难以逆转** — 之后改变想法代价很大
2. **没有上下文会令人惊讶** — 未来的读者会疑惑"为什么他们这样做？"
3. **真实权衡的结果** — 有真正的替代方案，你因为特定原因选了其中一个

如果三个中缺任何一个，跳过ADR。

## 使用场景
- 制定计划后压力测试
- 需求模糊或各方理解不一致时
- 上线前确认技术决策
- 重构前的现状评估
